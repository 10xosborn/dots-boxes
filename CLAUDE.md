## Firebase (project `dots-and-boxes-39e7e`, free Spark plan)

- **Sign-in:** anonymous. The site's domain must stay in Authentication → Settings → Authorized domains.
- **Firestore** (`(default)` database, Standard edition):
  - `users/{uid}`: `{name}`
  - `users/{uid}/scores/{id}`: one ScoreEntry per game, saved under the game's own id since PR #4 (the create-only rule stops a second save of the same game). `n` is 3–6 on a standard board or 0 on a custom one. The other fields are `rows`, `cols`, `custom`, `diff`, `result`, `ms`, `mine`, `theirs`, `xp`, `date`, `first`, `moves` and, on resumed games only, `resumed: true` (the rules don't restrict fields, so the published rules accept it).
  - `leaderboards/{n}_{diff}/players/{uid}`: `{uid, name, games, wins, best, rate}`. Standard boards only, updated in a transaction.
- **Realtime Database** (europe-west1): `rooms/{code}` holds `{host, guest, names, rows, cols, n?, first, game, moves, online}`.
  - `n` is still written for standard sizes so older clients keep working.
  - Joining a room uses a transaction.
  - **Presence (PR #5):** `presence/{code}/{uid}/{connectionId}` = server time, one child per open connection, set up again on every `.info/connected` (onDisconnect cleanup registered before the write). A player is present while any child exists. The old `rooms/{code}/online/{uid}` flag is still written (after any move transaction in flight lands, because a write inside the room cancels it) for older versions of the game; it decided presence until the owner published the `presence/` rules on 2026-10-13. Moves never wait for presence.
  - **Rejoin (PR #6):** at start-up a saved `dnb:room` is rejoined with one `get()` of `rooms/{code}` (`rejoinRoom()`: the room only if this anonymous uid still holds that seat), then the usual subscription and presence. A `get()` with no connection never settles, so the Online screen races it against 8 s and then offers "Try again". No rules change.
- **Server-checked turns (PR #25, open; the owner publishes the rules after merging):** rooms the game creates carry `v: 2`, `turn` (0 host, 1 guest), `count` and `drawn/{edge}: seat`; a move is one `update()` of `moves/{count}`, `drawn/{edge}`, `count + 1` and the next `turn` (`sendMove(code, e, n, { seat, next })`; Online computes `next` by replaying with the move), a rematch also resets `turn = first`, `count: 0`, `drawn: null`. `firebase/database.rules.json` is **generated** by `scripts/database-rules.mjs` (`npm run rules`; `npm run test:rules` runs `--check` first): for v2 rooms the room-level write is only creation, removal or a rematch after a finished game (count = E), and per-child grants cover guest (once), names/{who}, updated, online/{uid}, dbg, and moves/$n, drawn/$e, turn, count for the player to move; the move rule checks the next slot (`$n === count + ''`), a free in-range whole-number edge, its drawn entry with the mover's seat, count + 1, same game, and the next turn from box closure (edge-to-box arithmetic with % and /, child keys built as `(x) + ''`). Rooms without v keep the old rules (old copies play on). Known limits: an old copy can't move in a v2 room once published (publish a day after the deploy); a game spanning the publish with a stale copy having moved can stick; old rooms stay unchecked until a later rule refuses rooms without v (the owner's call, offered in #25).
- **Rules:** `firestore.rules` is the version published on 2026-09-29 (accepts old scores without `rows` and the current format; boards capped at 12×12). `database.rules.json` (PR #5's `presence/` rules) was **published by the owner on 2026-10-13**. Both files in the repo now match the console; any future rules change still needs the owner to publish it, and must keep both orders safe (rule 6).
- **Offline fallback:** if Firebase can't be reached, the app switches to the local adapter and shows a banner.
- **Not built yet:** the anti-cheat check, which would replay each score's saved moves on a server. It needs Cloud Functions, which need the paid Blaze plan, and the owner hasn't decided on Blaze.

## AI (`src/lib/engine/ai-core.js`)

**PR #20 (`ai/4x4-and-speed`, one commit `91d7fca`, opened 2026-10-20, open; the owner merges, see Open issues)** answers the owner's 2026-10-19 questions (100%?, a 4x4 opening book, 7x7 earlier control play, speed, online lag):
- **Exact search rewritten after Barker & Korf** (`node`/`quiet`, `forced` takes the boxes best play surely takes, `decisions` takes or declines each chain, one of each box's border lines, typed-array table `TS=1<<19` with two bounds and the best line, keyed by the canonical form under the board's 8 or 4 symmetries, simple loony endgames valued by `V`): 1.6-3.2x faster; reach `exactFrom` 26 (4x4) / 34 (5x5) / 44 (6x6) / 56 (bigger). Fixed a bug: with two chains to take, the old search only weighed declining the first (12 of 6,000 3x4 positions wrong; regression test vs brute force).
- **Pondering** (`ponder(g,d,sliceMs)`, `solved` map, `PONDER_EXTRA=4`, `PONDER_TURN=1000` ms per reply before rotating): on the player's turn vs Hard, `Game.svelte`'s `queueAI` calls `ponderAI` (worker only); the worker runs 40 ms slices (setTimeout between), stops on any message, after 20 s, or when nothing is left; `choose()` checks `solved` first. `onDestroy` calls `resetAI()` (stops it); after a reload into the player's turn the ponder starts 500 ms later (the benchmark showed 12-26 ms on a late-game reload under 4x CPU throttling when it started at load).
- **Pauses:** 250-450 ms before the AI's first line of a turn (was 300-800), 200-280 ms before each further line after it closes a box (`queueAI(again)`).
- **Results** (`ai:bench --slow 4 --ponder 2000`, 100 games): vs the original Hard 50/93/100/100/100% on 3x3-7x7 (4x4 93/6/1); vs PR #17's Hard 4x4 58/16/26, 5x5 67%, 6x6 60/15/25, 7x7 85%; vs Medium 97-100%. Pondering vs PR #17's Hard on 4x4 by player think time: losses 34% (none), 23% (1 s), 19-26% (2 s, three runs), 15% (4 s). Tested and rejected: earlier 7x7 control play (threshold 60/80/always: 79/71/67% vs 77% at 40), MOVE_MS 500/400 (weaker), the `leafExact` idea (no gain). 4x4 opening book: infeasible (hundreds of millions of positions, ~2 min each to solve at 33-36 left); 4x4 is a draw with perfect play (own solver, 1,010 s), so 100% is impossible against a perfect player.
- Browser (phone, CPU 4x): AI first line median 448 ms (main 701), chain lines 252 (629), a 4x4 game 19.9 s (26.2).

**PR #17** (`ai/stronger-hard`, merged by the owner on 2026-10-19 with #18) replaced Hard's strategy and tuned Medium. What #17 changed:
- Hard fights for control (Berlekamp's long chain rule): with 15 to 40 safe lines left it plays the safe-line race out many times for each safe line and each 1-2 box sacrifice (Monte Carlo, sequential halving); with 14-20 left (by board size) `raceBest` searches the race exhaustively, sacrifices included; above 40 it plays a random safe line. Chain values (`pchains`) split branching regions into their arms (right sign 91 of 107 test positions against exact search, the old `V` 35). Exact search starts at 26 lines left on 4×4, 32 on 5×5, 40 on 6×6 and up (whole game on ≤9 boxes), 0.4 s (1.5 s on 3×3), root pruning; ties go to captures, then safe lines, then the fewest boxes given away. Every Hard move has a 0.7 s wall-clock limit (`MOVE_MS`) in the worker; `createAI({timeScale})` scales it.
- Medium, when every line gives boxes away, draws the line that gives the fewest (`giveaway`); old Medium opened the smallest region at a random line.
- `ai.ts` loads the main-thread fallback engine only when the worker fails (dynamic import, quarter thinking time): the start-up script lost 8.7 KB gzip.
- `npm run ai:bench` (self-play: `--sizes`, `--games`, `--pairs` incl. `old-*` levels from git `--baseline 2f770e0`, `--slow 4` = a phone 4x slower) and `npm run test:ai` (Vitest: known endgames, random positions outside the exact window, exact 3×3).
- Benchmark (`--slow 4`, 100 games, 50-150 on 7×7): new Hard vs Medium 99/100/100/100/96% on 3×3-7×7; vs old Hard 50% (both perfect on 3×3), **75% on 4×4** (56% at full PC speed), 100% 5×5, 99% 6×6, **81% on 7×7** (122/150): the brief's 90% target is met on 5×5 and 6×6 only (owner told in the PR). Medium vs Easy 97-100%; new vs old Medium 48-59%. Phone browser test: every AI move within 0.83 s of the line before it (pause included), no long tasks.

The AI as first built (September 2026), kept for its history; where it differs, the PR #17 and #20 notes above are current (strategy, thresholds, time limits, table keys, the pause):
- **Easy:** takes a box about half the time, otherwise plays randomly.
- **Medium:** always takes boxes, and never gives a box its third side while a safe line exists.
- **Hard:**
  - Strategy: a safe-line race search once 14 or fewer safe lines remain, all-but-two / all-but-four hand-outs, and opening chains and loops in the cheapest order (nimstring values).
  - Exact search: negamax alpha-beta with a transposition table, 53-bit Zobrist keys and Barker–Korf pruning.
  - When exact search starts: the whole game on boards of 9 boxes or fewer; 26 lines left on up to 16 boxes; 24 on up to 25; 22 otherwise.
  - Time limit per search: 1500 ms on 3×3, 500 ms on other boards of 9 boxes or fewer, 300 ms on larger boards. The clock is checked every 2048 nodes.
  - A search that times out isn't retried until fewer lines remain (`failAt`, which resets each game). The transposition table is also emptied at the start of each game (`resetGame`), so memory stays around 10 MB.
  - 3×3 opening book (`BOOK_SRC`): **every** optimal move for every position with up to 4 lines drawn, from a full solve (1,693 entries, 6.8 KB). Rotations and mirror images share one entry: a position (bitmask, bit e = edge e drawn) is looked up by its canonical form, the smallest bitmask among its 8 symmetric copies. Entries are in ascending order of that bitmask, 4 base64url characters each (a 24-bit mask of optimal moves), so no keys are stored. Rebuild or check it with `scripts/opening-book.mjs`.
  - Variety: the book or the exact search gives every optimal move, and Hard picks one at random, preferring captures, then safe lines, among them. All 24 first moves on 3×3 are optimal (each loses 3–6). In the strategy phase on other boards, ties are random too: which free box to take first, and which of several equally cheap chains or loops to open.
- `Game.svelte` adds a 300–800 ms "thinking" pause before each AI move.
- **Test results (September 2026):**
  - Every board shape from 1×1 to 12×12 got only legal moves.
  - Hard beats Easy and Medium on boards of 4 or more boxes.
  - Hard's slowest move takes about 0.5–0.8 s.
  - About 2,500 Hard moves on small boards matched an exhaustive solver.
  - Hard vs Hard on 3×3 always ends 6–3 to the second player. With perfect play, 3×3 is a win for the second player.
  - After PR #3: 200 Hard vs Hard games on 3×3 all ended 6–3 to the second player with every move optimal, and all 200 had different openings. Hard's slowest 3×3 move is about 0.1 s (it was 0.07 s). Win rates against Medium on 3×5, 4×4 and 5×5 were unchanged over 200 games each.

## Custom boards (PR #2, merged 2026-09-29)

- Setup offers 3×3 to 6×6 plus Custom, where rows and columns (1–12 each) are set with steppers.
- The picker only allows sizes whose dots are at least 40 px apart on the current screen. That's about 7×7 (or 10×6) on a phone, 9×12 at 1280×800, and 12×12 at 1920×1080.

- Online, the host can pick any size. A guest whose screen can't fit the board gets a clear message instead of joining.

## Progression and saved data

- **XP** = round(BASE × DIFF × boardMult), plus 2 × the winning margin on a win.
  - BASE: win 60, draw 30, loss 15.
  - DIFF: easy 1, medium 1.5, hard 2.5.
  - boardMult: boxes / 9 on boards under 9 boxes, otherwise 1 + (√boxes − 3) × 0.4.
- **localStorage keys:** `dnb:cfg`, `dnb:settings`, `dnb:profile`, `dnb:scores`, and since PR #4 `dnb:active` (the AI or pass-and-play game in progress: `{v: 1, id, mode, board, diff, p2, first, moves, ms, savedAt}`, saved after every move and when the page is hidden; cleared on finish, Quit and Restart, and when a new game starts), and since PR #6 `dnb:room` (the online room to rejoin: `{v: 1, code, seat, savedAt, endedAt?}`, saved on create and join; cleared on Leave, when the room closes or is gone, or when the seat isn't this player's; ignored and cleared 24 hours after `savedAt` or 10 minutes after `endedAt`, which `roomEnded()` sets when a game ends and removes when a rematch starts; rejoining must not save it again, or the 10-minute clock restarts). Start-up order: `?room=` link, then a reloaded `dnb:active` game, then `dnb:room`. Keep them backward compatible and migrate old formats, as `loadCfg()` does for the old `{n}` setup.
- **sessionStorage `dnb:inGame`:** the id of the game this tab is showing. On start-up, if it matches `dnb:active`, the app reopens the game directly (a reload); otherwise Home shows "Continue your game" (a browser restart). Leaving the game screen clears the flag but keeps the game.
- **Resumed games** count for XP, stats, games and wins, but carry `resumed: true`: stats' fastest win and the leaderboard's `best` skip them, and the results say "Resumed games don't set fastest-win times." The clock pauses while the app is closed.
